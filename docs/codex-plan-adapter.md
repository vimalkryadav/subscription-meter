# Codex / ChatGPT plan adapter status

The adapter is implemented for offline protocol testing and is **disabled by default**. No OpenAI credential was read, no OAuth login was performed, and no real generation/tool continuation was verified during implementation. Hosted-app eligibility, the selected account's authorization and compatibility remain unverified. The documented open-source/local-host flow does not establish approval for this remotely hosted shared-account platform. See the [official SIWC overview](https://developers.openai.com/siwc/token-sharing-open-source).

The dedicated backend paths are `/openai/v1/responses` and `/openai/v1/models`; the public edge maps them under `/gateway/openai/v1/`. They return no application route while disabled. Anthropic's `/gateway/v1/...` routes remain unchanged. Each admitted request retains provider `openai`, configured account label `primary`, and route-derived client label `codex`; that client label is attribution metadata, not authenticated proof of client software.

Activation requires an explicit deployment configuration with `METER_OPENAI_ENABLED=true`, `METER_OPENAI_AUTH_MODE=siwc-plan`, `METER_OPENAI_ORIGIN=https://api.openai.com`, and a dedicated `METER_OPENAI_TOKEN_FILE` mounted only into the gateway. The token must be an OAuth access token authorized for the documented ChatGPT-plan flow. The adapter refuses API-key-shaped and platform-member credentials, never falls back to API billing, never follows redirects, and does not retry generation automatically. Token-shape checks do not validate OAuth grants; trusted OAuth provisioning/refresh is still required. Do not reuse an unrelated local Codex login credential or expose upstream credentials to members.

The [official inference contract](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference) uses the public Responses endpoint and requires a completed response event for successful generation. This implementation passes response bytes/tool calls through, reads `response.completed` usage, and distinguishes failures, quota errors, incomplete streams and missing usage. Input totals, cached reads/writes and reasoning subsets are retained without double counting. No tool instruction is executed on the gateway.

The request validator requires `store:false`, `stream:true`, explicit input history, and the [documented preview constraints](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations). HTTP continuation must send the required conversation/tool-result items; `previous_response_id` is rejected. Unsupported request fields and hosted tools are rejected. Model availability must come from the selected authorized account, not a hard-coded catalog.

Before enabling for members, verify approved provisioning on Coder, a real streaming generation, one client-executed tool continuation with matching call IDs, account/model identity, quota exhaustion, token expiry/renewal, member authorization, audit replay and provider-specific price interpretation. The current tests are generated wire-contract fixtures, not evidence of a successful live subscription integration.

The token-file reader is bounded to 16 KiB and rereads the configured file for each request, so an atomic replacement takes effect without restarting the gateway. It permits one final newline, rejects malformed bearer values, and never searches a user's Codex home directory. The transport sets JSON/SSE headers itself, strips member authorization/cookies/account-selection headers, preserves body bytes, and closes an unfinished upstream response at its deadline. Nested hosted-tool definitions and audio/video input are rejected. Conflicting terminal events, inconsistent token totals, oversized events and truncated streams cannot produce complete usage.

## Exact activation prerequisites

This is an HTTP adapter, **not an OAuth registration or refresh service**. The following remain external prerequisites; a configuration switch is not evidence that they have been satisfied:

1. Establish that the intended remotely hosted, multi-member use is supported. The [SIWC overview](https://developers.openai.com/siwc/token-sharing-open-source) links an interest form for remotely hosted apps. Its open-source/self-hosted examples do not establish permission for distributing one owner's plan across unrelated members.
2. Provision a separate registration for this app through the supported flow. A trusted provisioner must validate the authorization state, PKCE exchange, ID-token signature/issuer/audience/expiry/nonce and granted scopes, then retain the issued client ID and verified account identity. A normal Codex sign-in or an unverified token copied into a file does not perform these checks. Follow [registration and sign-in](https://developers.openai.com/siwc/token-sharing-open-source/sign-in); do not read or replace an unrelated Mac login.
3. Give Coder its own persistent opaque host ID. Transfer only the selected app registration over SSH, preserving Coder's host ID. The [self-hosted VM guide](https://developers.openai.com/siwc/token-sharing-open-source/self-hosted-vms) explains the loopback callback and transfer boundary. An SSH tunnel or a different browser/account can keep this separate from existing Mac credentials, but must still preserve the registered callback contract.
4. Operate one trusted renewal process on Coder. It must serialize refreshes, use the registration's issued client ID, retain the newest rotating refresh token and expiry/scopes together, and atomically publish just the current access token to the gateway's dedicated file. Keep the protected full OAuth record outside gateway audit data. See [accounts and sessions](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions). This repository does not implement that process; expired/revoked credentials fail upstream and generation is never retried automatically.
5. Add the explicit OpenAI environment entries **and** a read-only mount of a dedicated access-token directory to both application slots in a private Compose override. Mounting an individual file pins its old inode and prevents atomic replacement from becoming visible inside a container. Set `METER_OPENAI_TOKEN_FILE` to the file inside the mounted directory; keep the full OAuth/refresh record outside this directory. Adding values to `.env` alone does not pass them into containers. Neither Kafka worker nor browser receives these credentials. Keep the renewal record owner-only and all credential files outside Git.

After these prerequisites, perform a restricted live acceptance run before member access: account-specific model listing, one completed text response, a local tool call followed by its matching tool result/history, revoked/expired token handling and renewal, plus audit/usage attribution. The gateway can be enabled only for that test and returned to disabled if any check fails. A successful model listing alone does not verify completed inference or authorize the hosted use case.

## Client configuration after activation

Members use their platform key, never the upstream SIWC token. A Responses provider needs the deployed `/gateway/openai/v1` base URL, `wire_api="responses"`, `requires_openai_auth=false`, and `supports_websockets=false`. Set its `env_key` to an environment variable containing the member key. These settings adapt the [documented Codex app-server configuration](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server) to this authenticated proxy; the account-specific model and actual tool loop still require the live acceptance run. Use per-command configuration or a separate client profile so existing login settings remain untouched.

The proxy supports only HTTP `/responses` and `/models`. Query parameters, persistent response lookup, WebSockets, Files upload and transcription routes are not implemented. Requests must carry complete required history; no server-side response-ID continuation is synthesized.

Focused offline tests: `mvn -Dtest=OpenAIProtocolTest,OpenAIPlanTransportTest,GatewayServiceTest test`. During an unrelated frontend edit, add `-Dexec.skip=true` to run the Java checks without rebuilding frontend resources. Transport tests use a substituted HTTP client and synthetic credentials; they make no OpenAI requests.
